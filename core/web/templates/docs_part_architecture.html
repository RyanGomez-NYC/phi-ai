Records flow from the source EMRs through ingestion into the encrypted stores, where sensitive categories are fenced off. People and the AI assistant read through role gates; drafts return to the EMR only with a human signature; exports pass consent gates before anything leaves. Every box reports to the audit trail — including the gates' refusals.

1. How to read the picture

  • Nothing skips the gates. There is no path from the stores to a person, the AI, or another organization that does not pass a role, consent or signature gate.
  • The AI is inside the walls. PHI RAG reaches data only through the same audited, role-scoped tools people use; the foundation model receives only the excerpts the gates released for the current question.
  • Green in, orange out. Arrival is about completeness (watermarks, checkpoints, surfaced gaps); departure is about permission (consent gates, exclusion counts, refusals).

2. Component reference

2.1 Source EMRs

  • Role: data planes into the AI-native platform — Epic, Oracle Health, athenahealth, eClinicalWorks, MEDITECH, NextGen. Records arrive from them; signed documentation delivers back to them (the chart of legal record, as the law requires — the intelligence, governance and AI-ready data model live in this platform).
  • Inputs: signed write-back and configured deliveries.
  • Outputs: bulk extracts and streaming events.
  • Failure mode: vendor unavailability stalls ingestion — runs fail visibly, watermarks hold, and nothing downstream silently ages.

2.2 Bulk import

  • Role: population-scale arrival over the FHIR Bulk Data API.
  • Honors: each vendor's real seams — Epic's one-run-per-24h group export with no incremental mode, NextGen's absence of bulk entirely.
  • Emits: bulk.completed / bulk.refused.
  • Key property: the watermark — the timestamp of the last known-complete extract — advances only on a clean run, so a half-arrived population can never masquerade as the current state.

2.3 Streaming intake

  • Role: real-time arrival — ADT admissions and discharges, ORU lab results, X12 835 remittance — on partitioned feeds.
  • Key property: per-partition acknowledged checkpoints; a gap between checkpoint and latest offset is displayed with its exact range on the Streaming data screen.
  • Deliberate non-feature: gap interpolation. A pipeline that guesses what it missed is a data-integrity incident that has not been discovered yet.

2.4 Encrypt · store · index

Role: the only doorway into the stores. Every record — bulk or streamed — is (1) encrypted, (2) classified for sensitivity (sud_part2, mental_health, reproductive, hiv, genetic, or none; psychotherapy content routed to its separate store), (3) normalized (reference resolution, terminology mapping), and (4) indexed for retrieval. Key property: classification happens at the door, not at read time — a record's sensitivity is a stored fact, uniform for every downstream gate.

2.5 The stores

Role: the encrypted holdings — record store, audit store and the physically separate psychotherapy store, with the queryable index beside them (no clinical content in the index, by design). Key properties: no direct read path exists; every consumer goes through the gates; integrity checks — storage↔index reconciliation and full audit-chain verification — run as live operations, not annual rituals.

2.6 Role · consent · purpose gates

  • Role: the enforcement point every read crosses. Evaluates: the role's permissions (enumerated, no wildcards except the System Administrator's audited *), the record's sensitivity class against the reader's role and the applicable consent, and the session's purpose of use.
  • Outputs: released records, plus a withholding count for whatever was held back.
  • Emits: disclosure-family events on release, access.denied on refusal.
  • Key property: the gate cannot be bypassed by the AI — the assistant's tools call the same gate code the screens do.

2.7 The assistant (PHI RAG)

  • Role: plans retrieval, calls role-scoped tools, assembles gate-released excerpts, and produces cited answers.
  • Contract: answer only from retrieved records; cite every source; never assert absence from unretrieved documents; confirm before population sweeps; state withholdings; counts, never lists, on the population plane.
  • Controls: the Control panel's retrieval and live-call switches (off = the assistant refuses to read at all, and says so).
  • Emits: a query event per question, plus the tools' own events.

2.8 The foundation model

  • Role: the language model the assistant runs on, called over the model API (Anthropic API, AWS Bedrock or GCP Vertex) at temperature 0 with bounded output.
  • Receives: the system contract, a short conversation tail, the role's tool schemas, and gate-released excerpts — never a database connection, never bulk data.
  • Data terms: excerpts are used to answer the question, not to train models, under the organization's agreement with the provider.

2.9 People & screens

Role: the role model's profiles, each seeing exactly the screens its permissions allow (the full matrix is in Part I). Key property: screens check permissions, not roles — role composition changes without touching screens.

2.10 Human signature

  • Role: the signature rule's enforcement point. AI drafts queue; a licensed reviewer edits and signs; only the signed artifact acquires a write path to the EMR.
  • Emits: signature.committed. Deliberate non-feature: auto-commit, batch signing, or timeout-advance. A draft's only exits are a signature or a return.

2.11 Export managers

  • Role: the only doorways out — bulk delivery, ROI production and outbound feeds. Apply the consent & redisclosure gate, record exclusion counts, honor the destination's write surface, and track acknowledgment.
  • Emits: export.completed / export.refused.
  • Key property: the three outcomes (complete / failed / refused) are all first-class and all visible in run history.

2.12 The audit trail

Role: the append-only, hash-chained memory of everything above. Every component writes to it; nothing edits it; the Control panel re-derives the chain on every load and reports intact or the first broken row. Concurrent writers may fork the chain legitimately; verification understands forks and distinguishes them from tampering.

3. The cloud architecture

  • Envelope encryption. Every stored object under its own data key, wrapped by a KMS master key that never leaves the key service; key use is itself logged.
  • Isolated stores. Record objects, audit events and psychotherapy content in separate stores with separate access policies — the psychotherapy separation is infrastructure, not a WHERE clause.
  • Relational index + OMOP. The index serves the screens; the OMOP layer serves research-grade analytics on the de-identified plane.
  • IAM in depth. Roles enforced in the application AND as cloud IAM policy, with purpose of use as an IAM session tag — the storage layer can refuse a read whose purpose tag is absent.
  • A no-script web tier. script-src 'none': the screens execute no JavaScript; these diagrams animate as SVG markup.
  • Credential hygiene. Model-provider and vendor credentials live server-side in restricted stores, never in pages, never in the repository.
