API details

Every programmatic surface of the AI-native platform: the conventions they share, the retrieval tools the assistant calls, the model API behind it, the EMR-facing integration APIs, and vendor authentication. These APIs were designed for AI as the consumer — audit-before-data, role-scoped tool schemas, structured refusals — not adapted to it afterward.

1. Conventions

  • Audit before data. Every surface writes its audit event before returning data; a crashed request leaves its intent on the trail.
  • Refusals are data. A consent, rate-limit or write-surface refusal returns a structured outcome with the rule named — a legitimate result, not an exception.
  • State changes are POST + CSRF, enforced globally as an application dependency, never per-route.
  • Purpose travels — on every event, and as an IAM session tag in the cloud permission layer.

3. The model API

Provider-pluggable (Anthropic API, AWS Bedrock or GCP Vertex), configured per deployment; credentials live server-side and never in a page.

3.1 Request anatomy

Each turn sends: the system contract (the retrieval rules, the citation format, the refusal rules, the role's identity and purpose), a short conversation tail, the role's tool schemas, and the user's question:

POST [provider messages endpoint]
[server-side credential — an API key file or cloud IAM, never in a page]

{"model": "[the activated assistant model]",
 "max_tokens": [assistant_max_tokens — Control panel],
 "temperature": 0,
 "system": "[the retrieval contract]",
 "tools": [ ...role-scoped tool schemas only... ],
 "messages": [ ...conversation tail..., {"role": "user", "content": "..."} ]}

3.2 The tool loop

  1. The model responds with either final text or a tool_use block naming a tool and its input.
  2. The platform validates the tool exists for this role, executes it server-side (audit first, then query, then withholding), and returns a tool_result block.
  3. The loop repeats — typically one to four tool calls — until the model emits final text. The loop is bounded; a runaway loop terminates with the turn's partial work discarded and the query already audited.
  4. The final text renders with its citations. Answers are not stored; only the question enters prompt history.

3.3 Parameters and failure behavior

  • temperature 0 — deterministic drafting; clinical answers should not vary with the weather.
  • Bounded output and a short context tail — the model never accumulates an unbounded PHI context.
  • Failure ladder: retrieval disabled → structured refusal; live calls off / no credential → deterministic scripted fallback, labeled; API error → the error is stated, the question was already audited, nothing was read.

5. Ingestion APIs

FHIR Bulk Data Export (core/fhir/bulk_client.py): kickoff (GET [base]/Group/[id]/$export with Prefer: respond-async → 202 + status URL), polling (202 + X-Progress → 200 + manifest), NDJSON download, then encrypt-store-index with reference normalization and sensitivity classification at the door. Only a clean run advances the watermark. Vendor seams enforced per profile: Epic's one-run-per-24h group export with no incremental mode; Group-only export where a vendor documents only that; the absence of bulk entirely where a profile records none. Streaming intake: three inbound feeds — ADT (admissions/discharges/transfers), ORU (results as they finalize) and X12 835 (payment remittance) — each partitioned with acknowledged checkpoints. The protocol: each partition tracks checkpoint_offset (last event fully processed) and latest_offset (newest event seen); processing advances the checkpoint only after the event is durably stored. A gap — offsets seen but unacknowledged, as after a broker restart — is surfaced on the Streaming data screen with the exact offset range, and is never interpolated: an interpolated gap is a silent data-integrity failure wearing a healthy pipeline's clothes.

6. Export and delivery APIs

Bulk delivery (core/fhir/bulk_export, delivery/): scope → consent & redisclosure gate (psychotherapy never; Part 2 refuses without consent; sensitive categories excluded with counts) → package → deliver on the destination's write surface → complete / failed / refused, all recorded. ROI production: one filtered set, two artifacts — the FHIR Bundle and the Bates-numbered PDF — with included and withheld counts stored on the request. Write-back: only signed drafts acquire a write path (on Epic, a DocumentReference create attributed to the signer); the write-surface assertion refuses resource/interaction pairs the vendor does not expose. Outbound feeds: acknowledged sequences; held = queued and accounted; paused = governance, accumulating, never leaking.

7. Vendor authentication

Per-vendor detail with inline citations to each vendor's published documentation lives in EMR connections.

Epic — SMART Backend Services: RS384-signed JWT (iss = sub = client ID, aud = token endpoint, exp ≤ 5 min, single-use jti) exchanged for a short-lived token with system scopes; per-health-system enablement is per-resource and per-flavor, so the install runbook enumerates each write API individually. Oracle Health: system account with explicit per-resource scopes (wildcards unsupported) — a missing scope fails at the resource, so conformance is verified per-resource; the JWT assertion mode is the documented path for bulk. eClinicalWorks: the same asymmetric private-key JWT assertion as Epic — no client secret. athenahealth: OAuth2 client credentials with a client secret — the one profiled vendor whose documented flow is a secret. MEDITECH / NextGen: SMART Backend Services recorded as the ONC g(10) certification baseline, flagged for portal confirmation; NextGen exposes no documented bulk export and no bulk write surface, and the platform refuses accordingly rather than degrading. Every other profiled vendor ({{ vendor_names }}): the grant, signing algorithm, scope rule, bulk scope and write surface its own documentation records, held in its profile and listed on EMR connections; nothing is carried over from another vendor.
