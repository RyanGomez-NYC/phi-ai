# Epic non-production JWK Set

## Why this file exists

As of the Epic sandbox's current requirements (confirmed against Epic's
own OAuth 2.0 documentation - fhir.epic.com/Documentation?docId=oauth2\&section=JWKS-URLS - in August 2026), **static public key uploads are no
longer accepted for backend OAuth in the sandbox.** Epic on FHIR's own
timeline:

- August 2025: no new static key uploads accepted for the sandbox
- February 2026: static keys no longer supported in the sandbox at all;
  Epic on FHIR no longer allows static key uploads for new apps

This means the "paste your PEM public key into a form field" flow that
`scripts/generate_epic_keypair.sh`'s original guidance assumed **does not
exist as an option anymore** for this project's timeframe. Epic instead
requires a **JWK Set URL (JKU)** - a public HTTPS endpoint serving your
public key(s) in JSON Web Key Set format - configured on the app's
"Non-Production JWK Set URL" field.

## What this file is

`epic_jwks_nonprod.json` is the JWKS-format equivalent of
`epic_public_key.pem` (generated by `scripts/generate_epic_keypair.sh`).
It contains only the **public** key - the same information a PEM public
key file already discloses, just reformatted per RFC 7517. Publishing a
public key is not a security exposure; that is the entire point of
asymmetric cryptography. The private key never appears here and must
never be committed.

## The `kid` has to agree on both sides

`epic_jwks_nonprod.json` carries `"kid": "phi-ai-dev-2026"`.

A `kid` is a key IDENTIFIER, and its only job is to match. Epic stores
the JWK Set you registered and selects the verification key for an
incoming client assertion by looking up the `kid` in the assertion's JWT
header against the set it fetched from your JWKS URL. If the two ever
disagree, **every token request fails signature verification** - the
connector stops authenticating entirely, with an error that points at
crypto rather than at whatever actually changed.

So the rule is agreement, not any particular literal text: the value in
this file, the value in your `.env`, and the value Epic holds for your
app must all be the same string. Changing it means republishing this
file and re-registering with Epic in the same window. Rotating the
keypair is the normal time to do that.

## How to regenerate it

If you rotate your keypair, regenerate this file from the new
`epic_public_key.pem`:

```bash
python3 -c "
import json
from cryptography.hazmat.primitives import serialization
from jwt.algorithms import RSAAlgorithm

with open('epic_public_key.pem', 'rb') as f:
    public_key = serialization.load_pem_public_key(f.read())

jwk = json.loads(RSAAlgorithm.to_jwk(public_key))
jwk['kid'] = 'phi-ai-dev-2026'  # bump this on rotation - see the section above
jwk['use'] = 'sig'
jwk['alg'] = 'RS384'

print(json.dumps({'keys': [jwk]}, indent=2))
"
```

The `kid` value here must match `PHI_AI_FHIR_JWT_KID` in `.env`.

## Where this is registered

The raw GitHub URL for this file (e.g.
`https://raw.githubusercontent.com/<your-org>/<your-repo>/main/deploy/aws/epic_jwks_nonprod.json`)

> Substitute your own repository. The JWKS must be served from a URL you
> control: Epic fetches it to verify your client assertions, so whoever
> controls that URL controls what keys Epic will accept for your app.
is set as the app's **Non-Production JWK Set URL** in the Epic on FHIR
"My Apps" console. GitHub raw content is public HTTPS with no
authentication required, which is exactly what a JWKS endpoint needs to
be - Epic's authorization server fetches it directly to verify signed
JWT client assertions.

For a production connection with a real Epic customer, do not reuse this
sandbox JWKS - generate and host a separate production keypair/JWKS, per
`docs/EMR_CONNECTORS.md`'s guidance on never reusing sandbox keys in
production.
